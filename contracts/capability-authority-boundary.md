# Capability / Authority Boundary Contract

## Definitions

### Capability

Something the system can technically do.

Examples:

- read a repository;
- execute a test;
- edit a file;
- push a branch;
- sign a transaction;
- publish a message.

### Authority

Permission for a specific actor or runtime to exercise a capability under defined conditions.

### Request

A statement that an actor would like to use a capability.

A request is not authority.

### Effective capability

A capability that is both technically available and currently permitted in the active runtime context.

## Invariants

### Invariant 1 — capability does not imply authority

```text
can_do(X) does not imply may_do(X)
```

### Invariant 2 — generated code cannot self-grant

Source generated by a model cannot authoritatively expand the model's own effective capability.

### Invariant 3 — permission requests are evidence, not grants

A provider permission event proves that permission was requested. It does not prove that the request was approved or that the action occurred.

### Invariant 4 — authority widening is explicit

Any transition that broadens effective authority must be attributable to trusted runtime policy or explicit governance.

### Invariant 5 — denial is stable under provider behavior

Provider persuasion, repeated requests, fallback, or self-reported necessity must not transform a denied capability into an allowed capability.

### Invariant 6 — runtime truth outranks self-description

If a model claims it can or cannot perform an operation, the claim is advisory. Runtime capability state determines truth.

## Conceptual evaluation

```text
requested
  ∩ available
  ∩ policy_allowed
  ∩ operator_authorized_if_required
  ∩ scope_valid
  ↓
effective
```

## Consequence for generated specialists

A child specialist should begin with no assumed authority beyond the runtime contract explicitly projected to it.

Authority is not inherited merely because a parent, forge, or host has broader capabilities.

## Consequence for ToadAid MCP

Tools may exist in the MCP capability plane without being available to every session or specialist.

Tool discovery, tool availability, permission to invoke, and successful invocation are distinct facts and should remain separately observable where relevant.
